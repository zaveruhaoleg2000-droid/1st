# Технічна архітектура — GRAY ZONE: 1989 v0.0.2

## Головне правило

Симуляція **не залежить від виду/камери**. Графіка викликає функції симуляції, але не створює її реальних бойових подій. Усі юніти мають ID і глобальні координати, що зберігаються при зміні режимів.

```
Win32App / input (WINDOWS ONLY)
   ├── Simulation (C++ portable, WorkerPool <=4 threads)
   │   ├── Soldier[0..1600] / Squad[]
   │   ├── orders / AI / health / ammo
   │   └── Global coordinates, sector = floor(x/3000), floor(z/3000)
   └── Renderer (C++ portable, software triangle rasterizer + depth)
       ├── 3D terrain/procedural props
       ├── command LOD markers or near-field soldier geometry
       ├── perspective camera
       └── abstract strategic map
```

## Межі поточної версії

- Дані між секторами не зникають, бо збережені у світових координатах. Але cache/grid-chunk streaming ще немає. Геометрія генерується лише біля камери кожен кадр.
- Програмний 3D-рендерер не масштабується як GPU для великої сцени. Зараз корисний як контрольний бенчмарк і спосіб перевірити механіку до написання Direct3D 11 backend.
- Зараз рух у напрямку точки — пряма, а не шлях із уникненням перешкод.
- Модель вогню — демонстраційний алгоритм близькості, а не тактична модель реальної зброї.
- Покрокове планування ще не реалізоване: наразі фіксовані симуляційні тики, пауза, накази та передавання під ШІ.
- Вид за командира — камера над ним і рух одного бійця, а не FPS-шутер.
- Збереження — попередній формат v1 без міграцій, поточно вибране відділення не серіалізується; його ID повертається до 0 при завантаженні.

## Наступна технічна задача

1. Перенести існуючі команди рендерера в інтерфейс бекенда й реалізувати Direct3D 11 (GPU).
2. Відокремити `SectorStore` (3×3 км), додати висотні дані і кеш активних 3×3 секторів.
3. Реалізувати детерміноване збереження 16/32-бітних height-chunks, асинхронну генерацію.
4. Побудувати `SpatialHash` для локальних пошуків, потім навігацію і LOS.
5. Пізніше — фінанси ЧВК, контракти, справжня географія.
