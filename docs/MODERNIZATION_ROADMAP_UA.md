# План розвитку GRAY ZONE: 1989 після v0.0.23

Дата: 14.10.2026. Переглянуто актуальний код графіки, введення, рельєфу, симуляції, контрактів, кампанії, меню, діагностики, звуку та збережень. Це пропозиції для наступних версій; перелічені нові фічі ще не реалізовані.

Цільовий GPU: RTX 3050 Ti, 4 ГБ VRAM. Обсяг системної RAM та CPU користувача не уточнені. Зберігаємо C++20/CMake/Vulkan, CPU fallback, українську мову та сумісність збережень. Ціль 1080p/60 FPS потребує вимірювання на реальній карті; поточні тести на Mesa/Wine її не підтверджують.

## 2. Інтерфейс: native GPU HUD як перший крок

Візуальний напрямок: читабельний військовий інтерфейс 1989 року — темні напівпрозорі панелі, стримані оливкові/бурштинові акценти, чіткі піктограми та український текст. UI не повинен займати значну частину бойового екрана.

- Верх: назва контракту, активна ціль, пауза, покроковий/реальний режим, час і швидкість симуляції. Гроші — переважно в кампанії, щоб не перевантажувати бій.
- Низ: картки загонів із чисельністю, здоров'ям, боєприпасами, виконуваним наказом; кнопки руху й утримання позиції. Майбутні команди відображаються тільки після реалізації механік.
- Праворуч: компактна панель вибраного загону/об'єкта, підказки, повідомлення про результат і втрати.
- Кут екрана: minimap, ціль контракту, видимі дружні юніти; ворожі позначки згодом підпорядковуються розвідці/Fog of War.
- У світі: контур або кільце вибору, маршрут, точка наказу, зони цілі, іконки стану. Проєкція маркерів і picking використовують ту саму актуальну камеру, що й Vulkan draw.
- Меню: режим вікна, роздільність, VSync/обмеження FPS, масштаб UI, профілі high/medium/low, тіні, згладжування, матеріали, вітер і вода. Налаштування мають змінювати фактичний GPU шлях; зараз частина F6/F10/F12 стосується CPU, а GPU профіль задає launcher.
- Збереження: прев'ю слота, дата, сценарій, етап контракту, зрозуміле повідомлення про помилку.
- Доступність: UI scale 80–150%, контрастний режим, форми/піктограми поряд із кольорами; повноцінний Unicode замість побайтового трактування UTF-8.

Технічно: окремий UI pass після 3D, glyph/icon atlas, alpha blending, невеликі vertex/index batches. CPU fallback використовує ті самі UI дані. Не потрібно повертати повну CPU растеризацію сцени заради HUD.

Критерій готовності: меню → вибір контракту → висадка → вибір загону → наказ → видимий результат → збереження/завантаження проходять у native Vulkan; UI правильний після resize, зміни масштабу, камери та backend. Клік по юніту після повороту/zoom не залежить від попереднього CPU кадру.

## 3. Генеративний рельєф: розвиток чинної системи

Рекомендовано процедурний двигун із seed і правилами, який відтворює світ однаково після завантаження. Генерація нейромережевих зображень не потрібна для базового runtime: важливі повторюваність, шви секторів, керовані дороги й бойові зони.

Послідовність генерації:

1. WorldSeed + GeneratorVersion + координати сектора + параметри регіону.
2. Великі форми: рівнини, пагорби, долини; domain warp із обмеженою амплітудою.
3. Гідрологія: русло, берег, заплава, водна поверхня; мінімум починаємо з керованої spline-річки, а не повної фізичної ерозії.
4. Маски висоти, ухилу, вологості, ґрунту та біому.
5. Дороги/мости/майданчики будинків: врахувати ухил і водойми, вирівняти майданчики без розриву heightmap.
6. Візуальні матеріали та розміщення рослинності, каміння, селищ. Єдині правила виключають дерева з води, доріг і будівель.
7. Спільні дані для collision, navigation та укриттів; рендеринг не створює незалежну «фізичну землю».
8. Cache готового сектора на диску; фонові задачі й обмежена черга завантаження.

Початкові регіони: поля/села, ліс/пагорби, заболочена долина; потім промислові райони. Сюжетні майданчики сценарію задаються як керовані обмеження, щоб важлива переправа чи архів завжди були прохідними.

Для GPU варто перенести генерацію в mesh chunks із постійними ID. Уже є основа 16×16 chunks по 187,5 м у CPU renderer; native renderer зараз будує сітку біля камери. Розділити WorldGenerator, TerrainStore, TerrainStreamer, TerrainMaterialBuilder і PlacementSystem. Спершу CPU background generation, потім — GPU compute лише якщо профіль показує потребу.

Критерії готовності: однаковий seed дає однакові сектори за різного порядку завантаження; краї heightmap і масок збігаються; немає геометричних/текстурних швів; камера не запускає синхронну генерацію; cache eviction коректний; старі saves зберігають стару версію світу.

## 4. Земля: макротекстура + детальні матеріали

Рекомендована схема: унікальна низькочастотна макротекстура на сектор 3×3 км, маски поверхонь і окремі повторювані матеріали для близького плану. Одна велика картинка сама по собі не дає дрібної трави, рельєфу каміння чи правильної шорсткості.

| RGBA8 без GPU compression | Крок на 3 км | Один tile з повними mip-рівнями | Дев'ять однакових tiles |
| --- | --- | --- | --- |
| 2048×2048 | ≈1,46 м/texel | ≈21,3 МіБ | ≈192 МіБ |
| 4096×4096 | ≈0,73 м/texel | ≈85,3 МіБ | ≈768 МіБ |
| 8192×8192 | ≈0,37 м/texel | ≈341,3 МіБ | ≈3 ГіБ |

Це лише color maps. Normal/roughness/masks, staging, mesh, render targets і swapchain додадуть пам'ять. PNG/JPEG або ZIP зменшують файл на диску, не розмір декодованої GPU текстури. BC1/BC7 для color, BC5 для normal та BC4 для masks — наступне окреме покращення з перевіркою підтримки й uncompressed fallback.

Для RTX 3050 Ti 4 ГБ:

- Почати з 2048 макротекстури; high може мати 4096 для найближчого сектора, сусідні — 2048 або нижчі mip-рівні. Високий+вісім середніх tiles — близько 256 МіБ color maps без compression.
- Поблизу залишити окремі 512/1024 матеріали трави, сухої землі, багна, піску, каменю та дороги. 1024 вводити тільки після перевірки видимого виграшу й бюджету.
- Макротекстура задає плями поля/ґрунту/берега; detail color, normal та roughness читаються у своїх світових масштабах. Маски height/slope/moisture/road визначають змішування, а не довільний колір трикутника.
- Додати stochastic tiling або узгоджене змішування кількох UV масштабів, щоб прибрати смуги повторення. Перевіряти стабільність похідних/LOD та меж секторів.
- На скелях використовувати triplanar sampling, щоб текстура не розтягувалася на схилах; дорожні смуги/колії й плями додавати як decals/маски.
- Mip-рівні, анізотропія та плавні переходи обов'язкові. Virtual texturing відкласти до підтвердженої проблеми пам'яті на великому світі.

У поточному коді TextureLibrary приймає тільки 128/256/512, а Vulkan material array фіксований 512px. Макротекстури 2048/4096 потребують окремого asset/descriptor/streaming шляху; підміна наявного файлу великою картинкою цього не реалізує.

Критерії готовності: той самий сектор виглядає узгоджено з 10, 50, 250 і 1500 м; немає помітних плиткових смуг і швів; дорога відповідає дорожній масці; берег має пісок/багно, скелі — камінь; нові textures не викликають стрибок пам'яті або повторне повне mesh upload.

## 6. Етапи, залежності й результати

### Етап A — керування та інтерфейс

GPU HUD, спільна CameraState для draw/picking, маркери, minimap, ціль контракту й налаштування. Одночасно уточнити метрики кадру та додати benchmark. Результат — playable native Vulkan vertical slice без необхідності вгадувати стан бою.

### Етап B — вигляд землі

Односекторний prototype макротекстури 2048/4096 + masks + detail normal/roughness. Порівняти камери й профілі, зафіксувати формат матеріалів. Результат — відчутне покращення землі до будівництва великої системи генерації.

### Етап C — генеративний світ

Seed/version, регіони, русла, дороги/майданчики, shared masks, background jobs, GPU chunks, дисковий cache. Масштабувати матеріали етапу B на кілька секторів. Результат — відтворюваний світ без швів і синхронних зависань при русі камери.

### Етап D — тактика та інтерактивність

Collision/nav → LOS/укриття → події бою → пози/зброя/AI → один інтерактивний тип техніки. Кожна зміна розширює save schema та regressions. Результат — графіка й рельєф реально впливають на рішення гравця.

### Етап E — кампанія та контент

Різні шаблони цілей, контрактна дошка, ростер/лікування/логістика, причинні події, місійний звіт. Результат — різні сценарії мають різну механіку й наслідки, а не лише інший текст.

### Етап F — художня якість та випуск

Професійні моделі/анімації, local lights/particles, вибраний post-processing, художня різноманітність світу, spatial audio. Публікувати Windows ZIP тільки після перевірки пакетованого native/CPU шляху та реального benchmark.

## 7. Продуктивність і перевірка

- Розвести wall-clock FPS, CPU scene/simulation time, GPU timestamps, present wait і frame limiter; показувати p50/p95/p99 та 1% low. Не видавати reciprocal work-time FrameMeter за реальний FPS.
- Тестові сцени: селище, ліс, берег, дощ/сніг, 96/192/800 бійців, рух камери між секторами, холодний і теплий cache.
- Орієнтир для 4 ГБ VRAM: проектний бюджет resident GPU resources спочатку ≤1,5–2 ГіБ, із запасом для драйвера/swapchain/OS. Це майбутній бюджет, а не поточне виміряне споживання. Матеріали, macro maps, геометрія й render targets мають окремі ліміти; textures staging не тримається постійно.
- Перевірити frustum culling, instancing, chunk cache та LOD до дорогих post effects. Кілька кадрів у роботі вводити після коректності UI/resources і перевірки synchronization validation.
- Новий генератор: golden seeds, крайові семпли, порядок завантаження, disk cache, старі saves. Нова навігація/LOS: маршрути, схили, перешкоди й вогонь через стіну. UI: правильний picking після руху камери, resize й backend switch.
- Windows smoke із готової папки, Linux validation та тестовий запуск на фізичній RTX 3050 Ti завершують етап. Якщо конкретна конфігурація не вкладається в бюджет, знизити preset, а не заявляти гарантовані 60 FPS.

## 8. Перші десять задач

1. Актуальна спільна CameraState, незалежний від CPU draw picking.
2. Native UI pass із текстом, іконками й alpha blending.
3. Панель загону, ціль, пауза й накази у світі.
4. GPU налаштування в меню та коректні метрики/benchmark.
5. Prototype 2048 macro map одного сектора та world-aligned mask.
6. Detail color/normal/roughness, anti-tiling, порівняння з 4096 high.
7. WorldSeed/GeneratorVersion і сумісність старої heightmap генерації.
8. Chunk IDs, CPU background generation, disk cache й обмеження uploads.
