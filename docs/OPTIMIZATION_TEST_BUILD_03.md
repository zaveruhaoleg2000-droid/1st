# GRAY ZONE: 1989 — Optimized Test Build 03

**Дата:** 13.10.2026. **База:** Test Build 02. **Статус:** перевірено на Linux, Windows потребує збірки й перевірки.

## Що було виправлено

1. **Thrashing кешу висот.** `Renderer` використовує `TerrainWorld(16)` замість 9 секторів. У стандартній тактичній сцені кешу тепер вистачає: повторні кадри не генерують ті самі сектори знову.
2. **Повільна процедурна генерація.** У `HeightMap::generate` попередньо обчислюються координати для трьох октав шуму, запам'ятовуються значення кутів комірок шуму, а параметри русла річки обчислюються один раз на рядок. Формула рельєфу не змінена.
3. **Дублювання читань висот у трикутниках.** Один чанк сітки отримує спільну таблицю висот до 17×17: сусідні трикутники та вертикальні спідниці використовують одні й ті самі значення.
4. **Повільне завантаження з диска.** Бінарні карти `.gzt` на little-endian машинах читаються/пишуться одним блоком. 16-бітні `.pgm` зчитуються у буфер і перетворюються одним циклом. Перевірки розміру, CRC та EOF збережені.
5. **Холодний старт.** У `assets/terrain` постачається 20 секторів навколо стартової тактичної локації (один — редагований PGM, 19 — підготовлені GZT). Старі редаговані файли не перезаписуються. Можна відтворити командою `grayzone_terrain_tool bake-spawn assets/terrain`.

## Вимірювання

Ізольований CPU-рендерер, тестова Linux-машина, сцена з камерою (3000,1250), дистанція 1650, 96 солдатів; 640×400. Цифри приблизні, залежать від частоти CPU та дискового кешу:

| Тест | Test Build 02 із 16-секторним кешем | Test Build 03 з підготовленими секторами |
|---|---:|---:|
| Перший тактичний кадр | ~920 мс | ~68–75 мс |
| Наступні кадри | ~28–30 мс | ~25–27 мс |
| Згенеровано секторів при першому кадрі | 13 | 0 |
| Кеш висот | ~28 МіБ | ~28 МіБ |
| Глобальна карта 640×400 | ~7–9 мс | ~7–9 мс |
| Генерація одного неготового сектора | ~65–75 мс | ~22–25 мс |

**Сумісність:** порівняно всі ~1,05 млн пікселів у кожному з трьох різних секторів: жодної різниці між еталонним і оптимізованим генераторами. Контрольні 640×400 CPU-кадри також збіглися побайтово (0 змінених байтів із 768 015 у PPM).

**Тести:** 17/17 в CTest (16 попередніх + `optimized_terrain_exactness_and_cache`), Linux X11 smoke, перевірки карти, аудіо, збережень, сценаріїв. Це НЕ підтвердження GPU FPS або роботи на Windows.

## Повторити локально

```
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build --parallel 4
ctest --test-dir build -j 4 --output-on-failure
cd /path/to/project
./build/grayzone_benchmark 20 640 400
```

На Windows: `build_windows.bat`, потім у `dist` виконати `grayzone_benchmark.exe 20 640 400`. Бенчмарк вимірює лише CPU-рендерер без часу передачі кадру на екран. Вимір реальної Direct3D 11 продуктивності необхідно зробити на Windows-ПК.

## Що лишається

- Сектори поза початковою областю створюються при першому запиті (близько 22–25 мс на сектор на тестовому CPU). Для повністю плавного пересування між регіонами потрібне асинхронне попереднє завантаження з окремим бюджетом пам'яті.
- Дальші покращення: GPU профайлінг Direct3D 11; коректні LOD/відсікання геометрії; контроль p95 кадру в реальному вікні; довге тестування пам'яті на Windows.
- Сюжетні та стратегічні механіки залишаються прототипними, як у Test Build 02. Оптимізація навмисно не змінює ігрову логіку.
